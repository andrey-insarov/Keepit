# The `.keepit` file format

A `.keepit` file is a password-protected archive of a Keepit installation's data: clipboard history,
templates and (optionally) settings. It is what *Save to Archive…* (2.x: *Export…*) writes, what *Restore…* (2.x: *Import…*) reads, and — from
Keepit 3.0 — what automatic backups produce.

This document is the contract. The file format is **not** the storage format: how Keepit keeps the
same data on disk (`history.json` today, possibly a database later) is an implementation detail and
must never leak into `.keepit`. Any reader that follows this document can open any file Keepit has
written; conformance is checked against the reference files in `Tests/KeepitTests/Fixtures/`, which were
produced by an independent implementation (`Scripts/make_fixtures.py`) and are never regenerated by
the Swift code they test.

Two things are versioned separately:

- the **container** (how bytes are laid out and encrypted) — `format` 1 or 2;
- the **payload** (the JSON inside) — `payload.version`, currently 1.

A reader checks both. Changing one does not require changing the other.

## Conventions

- Byte order: there are no multi-byte integers in the container except where stated (big-endian).
- Lengths and limits are inclusive maxima unless stated otherwise.
- "Reject" means: the file is not opened, nothing is changed, the user sees that the file is not a
  usable backup. A reader must reject before doing anything expensive (key derivation, decompression).

## Container, format 1 (Keepit 2.0 – 2.13)

```
offset  size  field
0       8     magic   "KEEPITBK" (ASCII)
8       1     format  0x01
9       16    salt    random, used for the KDF
25      ...   sealed  Vault.encrypt(LZFSE(payload JSON)) — see below
```

`sealed` = `"KEEPITENC1"` (10 bytes ASCII) followed by AES-256-GCM *combined* output:
`nonce (12) | ciphertext | tag (16)`, as produced by CryptoKit's `AES.GCM.seal(...).combined`.
There is no additional authenticated data.

Key: `PBKDF2-HMAC-SHA256(password, salt, rounds = 200 000, dkLen = 32)`. The round count is a
constant of format 1 and does not follow any later default. The password is the exact UTF-8 bytes
the user typed (no normalisation, no trimming).

Compression: Apple LZFSE, the raw stream as written by `NSData.compressed(using: .lzfse)` (the
`bvx` block format, no container).

Reader rules:

1. `magic` ≠ `KEEPITBK` → reject (not a backup).
2. `format` unknown to this reader → reject with "needs a newer Keepit".
3. File larger than `Limits.dataFileMaxBytes` (512 MiB) → reject.
4. Derive the key, open the GCM box. Authentication failure → "wrong password" (the file may also be
   corrupt; the two are indistinguishable by design).
5. Decompress with a running limit of 512 MiB on the output; exceeding it → reject.
6. Decode the payload (next section).

**What the 2.x reader actually does** (Keepit 2.0 – 2.13, `Backup.decode`), for the record: rules
1–4 as above, except that a body without the `KEEPITENC1` prefix was returned as plaintext (the
3.0 reader rejects it); the decompressed size is checked *after* full decompression, not during it; the
payload's `version` field is decoded but not enforced; `Import…` applies the restored `settings`
object whole, including the trust-related keys listed under *Settings*. The 3.0 reader (stage 2 of
the 3.0 plan) implements the rules as written here; files written by 2.x are unaffected either way.

## Container, format 2 (Keepit 3.0)

```
offset  size   field
0       8      magic         "KEEPITBK"
8       1      format        0x02
9       4      headerLength  big-endian UInt32, ≤ 65 536
13      hl     header        UTF-8 JSON, exactly headerLength bytes (see below)
13+hl   12     nonce         AES-GCM nonce, fresh random per file
25+hl   ...    ciphertext    AES-256-GCM over LZFSE(payload JSON)
last    16     tag           AES-GCM tag
```

**Additional authenticated data** = the `header` bytes exactly as they appear in the file. A reader
must pass those bytes to GCM unchanged; it must not parse the JSON and serialise it again (field
order and whitespace would differ). A modified header therefore fails authentication.

The header is JSON with these fields:

| field | type | required | meaning |
|-------|------|----------|---------|
| `mode` | `"auto"` \| `"manual"` | yes | how the key is derived (below); part of the AAD, so it cannot be swapped |
| `kdf` | string | yes | `"pbkdf2-hmac-sha256"`; anything else → reject |
| `rounds` | integer | yes | 1 000 … 5 000 000; outside → reject before deriving |
| `salt` | base64 | yes | 16 bytes |
| `recovery` | object | no | `{salt, wrappedKey, wrappedEntropy}` as in `vault.json`, base64 fields; only in `auto` mode |
| `created` | string | yes | ISO 8601 UTC |
| `app` | string | yes | e.g. `"Keepit 3.0.0"` |
| `minReader` | string | yes | lowest Keepit version that can read this file, e.g. `"3.0"` |
| `label` | string | no | user-chosen device label (off by default); ≤ 64 characters |
| `sourceID` | string | no | random UUID of the installation (auto mode); not a hardware or user identifier |
| `backupID` | string | no | random UUID of this file (auto mode) |

Limits: `headerLength` ≤ 65 536; `salt` 16 bytes; recovery fields ≤ 256 bytes each; unknown header
fields are ignored (and still authenticated, being part of the bytes).

**Key derivation.** Two modes, both AES-256-GCM with the key below:

- `manual` (*Save to Archive…*, 2.x *Export…*): the user types a password for this file. `salt` is fresh and random,
  `rounds` is whatever the writer chose (3.0 writes 200 000). Key = PBKDF2 as in format 1.
  No `recovery` block. Does not depend on the vault being enabled.
- `auto` (automatic backup): the file is opened with the **Keepit vault password** of the
  installation that wrote it. `kdf`, `rounds`, `salt` are copied from that installation's
  `vault.json`, so a reader derives the same *data key* from the same password.
  Backup key = `HKDF-SHA256(ikm = data key, salt = empty, info = "keepit-backup-v2", L = 32)`.
  The data key itself is never the file key. If the installation has a recovery phrase, its
  recovery block is copied into the header: a reader can derive the data key from the 24 words
  (HKDF of the entropy with the block's salt and info `keepit-recovery-v1`, then unwrap
  `wrappedKey`) without any `vault.json`. The GCM tag is the only proof that a key is right; a
  matching salt is merely a reason to try the key already in memory.

Reader rules: as for format 1, plus: `headerLength` and header limits are checked before JSON
parsing; `rounds` is range-checked before PBKDF2; `minReader` above the reader's version → reject
with "needs Keepit X or newer" (not "corrupt"); `mode` unknown → reject. After a password or
recovery phrase has opened the file, the reader may show counts and contents; before that, only
`created`, `label` and the file size may be shown, marked as unverified.

What the storage provider sees: everything in the header (date, app version, KDF parameters, the
wrapped recovery material — which is useless without the phrase — and the optional label), the
file size, and nothing of the content. Identical payloads produce different files (fresh nonce,
fresh `backupID`), so the provider cannot tell whether two backups have the same content.

## Payload (JSON inside the container), version 1

```json
{
  "version": 1,
  "created": "2026-11-03T10:12:45Z",
  "app": "Keepit 2.13.1",
  "history": [ ClipItem, ... ],
  "templates": TemplateNode,
  "settings": Settings | absent
}
```

Encoding: JSON, UTF-8. Dates are ISO 8601 (`yyyy-MM-ddTHH:mm:ssZ`, UTC, as written by
`JSONEncoder.dateEncodingStrategy = .iso8601`). Binary data is base64 (standard alphabet, padded).
Keys are sorted; whitespace is insignificant. The payload must stay below 512 MiB decompressed.

**Validation (3.0 reader).** After decoding, before anything is returned: every item has at least
one format; text ≤ 50 MiB, RTF/HTML ≤ 200 MiB, PNG ≤ 100 MiB and ≤ 40 megapixels by header, file
list ≤ 10 000 entries — these are the *ceilings* of the corresponding settings, so whatever any
installation could record will restore; a user's narrower settings govern recording only, and no
limit is ever taken from the backup itself; `sourceApp` ≤ 255 characters; `contentHash` matches the rule above; ids are unique;
templates ≤ 5 000 nodes, ≤ 16 deep, names ≤ 200 characters, ≤ 50 hot keys. Known formats must be what
they claim (3.0.4): `public.utf8-plain-text` is valid UTF-8, `public.rtf` starts with `{\rtf`,
`public.html` is UTF-8 or begins with a UTF-16 byte-order mark, `public.png` carries the PNG
signature, every entry of a file list is an absolute path without NUL and ≤ 4 096 bytes; any other
UTI is opaque bytes under the size limit. A violation is `invalidContent`, naming the rule. Settings
are clamped on apply, not rejected. The app applies the same rules to its own `history.json` and
`templates.json` when they load, and to every item a store takes from anywhere else.

**Compatibility rules.** A reader ignores fields it does not know. A writer must not change the
meaning or type of an existing field; new fields are optional with a defined default. Breaking
changes bump `version`, and a reader rejects a payload version it does not know (3.0 reader; the
2.x reader does not check it). Readers also enforce `Limits` (item counts, template depth and count,
image pixel caps) exactly as they do for live data — a backup is untrusted input.

### ClipItem

| field | type | required | notes |
|-------|------|----------|-------|
| `id` | UUID string | yes | identity across Merge |
| `date` | ISO 8601 | yes | when copied |
| `formats` | object: UTI → base64 | yes | at least one entry |
| `sourceApp` | string | no | bundle identifier of the app it was copied from |
| `contentHash` | hex string (64) | yes | SHA-256 of the primary format's bytes (see below); used for duplicate detection |

Known UTIs: `public.utf8-plain-text` (UTF-8 text), `public.rtf`, `public.html`, `public.png`,
`com.it.keep.file-list` (JSON array of absolute paths, UTF-8). Readers keep unknown UTIs as opaque
data. Primary format for hashing: file list, else text, else PNG, else the format whose UTI sorts
first by byte value.

Kind is derived, not stored: file list → `files`; PNG present and plain text absent or shorter than 200 characters → `image` (browsers add a URL or alt text next to a copied picture); otherwise `text`.

### TemplateNode

| field | type | required | notes |
|-------|------|----------|-------|
| `id` | UUID string | yes | |
| `name` | string | yes | `""` → show the content's title; `"-"` → separator; ≤ 200 characters |
| `clip` | ClipItem | no | absent → folder |
| `hotKey` | `{ "keyCode": int, "modifiers": int }` | no | Carbon virtual key code and modifier mask |
| `children` | array of TemplateNode | yes | empty for items |

The root node is a folder whose `name` is ignored. Depth ≤ 16, total nodes ≤ 5 000.

### Settings

The same keys as `settings.json`; every key optional, missing keys take the reader's defaults
(exactly as `Settings.init(from:)` does). A 3.0 restore **never** applies these keys from a backup,
because they express trust in a particular installation, not user preferences:
`allowURLCommands`, `trustedURLSenders`, `biometricUnlock`, `biometricPasswordChange`, the backup
folder bookmark and any key holding a local path. (The 2.x *Import…* applies the object whole —
see the note under format 1.) Readers from other platforms may ignore the whole object.

## Reference files

`Tests/KeepitTests/Fixtures/` holds files produced by `Scripts/make_fixtures.py`, a Python implementation of
this document that shares no code with Keepit. Each file has a sidecar `<name>.json` describing the
password (or that there is none), the expected outcome and, for readable files, the expected
content. The Swift test suite opens every fixture and compares. The fixtures are committed and are
**not** regenerated by CI: if the Swift reader and the Python writer ever disagree, the test fails,
which is the point. When a new format or payload version is added, new fixtures are added; existing
ones are never modified.
